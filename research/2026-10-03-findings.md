# What keeps agent PRs correct: research and measurements, 2026-10-03

Produced with the [research skill](../.cursor/skills/research/SKILL.md). Every number below is either
measured on this repository's history with the scripts in this directory, or linked to a source that
was opened and read. Grades: A measured with a stated method and sample, B numbers without a method
or self-reported by the party that benefits, C opinion or anecdote.

## TLDR

The decision: which practices from pstack (Lauren Tan's skills plugin) and from other teams should
vibe-verifier adopt to keep agent-written PRs correct, keep codebase patterns intact, and ship faster.

The finding that drives it: **the catalog's gates catch hygiene problems, not the defects that cause
rework.** Replaying 59 merged PRs through today's gates, the security, workflow, and ratchet gates
fired on none of the 17 PRs whose lines a later fix rewrote. PR size alone flagged 12 of them. The
published evidence points the same way: agents mostly fail by breaking existing behavior and by
writing tests that assert little, and executable checks hold agents to a rule where written
instructions decay. So the highest-value additions are an outcome metric, a regression lane in the
QAE harness, and test-quality signals, in that order.

## The three questions, answered

**How do you make a codebase's patterns hard to break?** Encode the pattern as an executable check
whose failure message names the fix, and make the nearest examples follow it. Instructions alone
decay: in 1,650 Claude Code sessions, compliance with a config-file rule fell about 5.6% per
function generated, and no file-structure choice helped ([McMillan, 2026](https://arxiv.org/abs/2605.10039), A).
Context files did not raise task success on SWE-bench Lite or a second benchmark while raising cost
by over 20% ([Gloaguen et al., 2026](https://arxiv.org/abs/2602.11988), A). Compiling AGENTS.md rules
into executable checks reached 88.3% constraint compliance against 67.0% with the prompt alone, over
300 tasks ([ContextCov, 2026](https://arxiv.org/html/2603.00822v2), A, single author). OpenAI writes
its custom lint messages "to inject remediation instructions into agent context", and reports that
"Codex replicates patterns that already exist in the repository, even uneven or suboptimal ones"
([OpenAI, 2026-02-11](https://openai.com/index/harness-engineering/), C). pstack's `/correct` skill
and its encode-lessons-in-structure principle say the same thing.

**How do bots add features without breaking others?** Check the old behavior, not only the new.
When agents implement features, 73.6% of analyzed failures were "regressive implementation"
([FeatBench, 2025](https://arxiv.org/abs/2509.22237), A). A map from code to the tests that cover it
cut the share of previously passing tests an agent broke from 6.08% to 1.82%, while TDD instructions
alone raised it to 9.94% ([TDAD, 2026](https://arxiv.org/html/2603.17973v1), A, small model and
sample). Of 86,156 agent-written test patches, 80.2% carried weak or no oracle signals
([2026](https://arxiv.org/abs/2606.18168), A). Maintainers would not merge roughly half of the agent
PRs that pass SWE-bench's tests; the automated grade ran 24.2 points above the merge decision
([METR, 2026-03-10](https://metr.org/notes/2026-03-10-many-swe-bench-passing-prs-would-not-be-merged-into-main/), A).
vibe-verifier's QAE harness checks only the new behavior a PR's own criteria describe. pstack's
answer is a maintained feature map per app plus a regression run on trunk.

**How do you ship faster without shipping broken?** Small PRs, fast local checks, and a capped fix
loop. Stripe merges over 1,300 agent-only PRs a week with local lints under five seconds and "at
most two rounds of CI" before a human takes over ([Stripe, 2026-02](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2), B).
AI reviewers' recall falls to 30% on PRs over 1,000 lines ([Martian Code Review Bench, 2026-04-16](https://withmartian.com/post/measuring-the-software-factorys-inspection-line), A).
Within a repository, a merged agent PR with ten times the commits carried 6.1 times the odds of a
verified follow-up fix ([2026](https://arxiv.org/abs/2609.26847), A). A second independent reviewer
raised defect coverage from about 47% to about 72%, with diminishing returns after
([Stone, 2026](https://zenodo.org/records/21328807), A, one organization, preprint).

## Experiments on this repository

All four ran here, are rerunnable with the scripts in this directory, and use only public history.

### 1. Outcome baseline (`pr_outcomes.py`, 14-day window)

| Repository | Merged PRs | Fix PRs | Feature and fix PRs a later fix rewrote | Median open to merge |
|---|---|---|---|---|
| vibe-verifier | 30 | 15 (50%) | 11 of 24 (46%) | 7 minutes |
| zack.land | 43 | 11 (26%) | 6 of 35 (17%) | 7 minutes |

The PRs a later fix rewrote had a median of 297 changed lines in vibe-verifier against 53 for the
rest, and 126 against 39 in zack.land. Every zack.land PR merged since it subscribed to the gates
(its PR 57, 2026-09-23) is CI configuration or a pin bump, so a before-and-after comparison of the
subscription is not possible yet.

Limits: SZZ (blame the lines a fix changed) is noisy. On Apache projects only about half of the
commits SZZ labels as fixes were fixes ([Herbold et al., 2022](https://link.springer.com/article/10.1007/s10664-021-10092-4), A).
Here fixes are labelled by PR title, and a fix that rewrites a line is not proof the line was a
bug. Bigger PRs own more lines, so they are blamed more often by chance.

### 2. Gate backtest (`gate_backtest.py`, n = 59 feature and fix PRs, 17 later fixed)

| Signal | Flagged | Later fixed among flagged | Later fixed caught |
|---|---|---|---|
| gitleaks, actionlint, zizmor, cognitive-complexity, max-file-lines | 0 | n/a | 0 of 17 |
| new-source-has-test | 7 | 3 | 3 of 17 |
| more than 100 changed lines | 22 | 12 (55%) | 12 of 17 |
| more than 200 changed lines | 16 | 9 (56%) | 9 of 17 |
| more than 5 files | 17 | 10 (59%) | 10 of 17 |

The base rate is 29%, so a size flag roughly doubles the chance that a PR needs a follow-up fix.
`build-tools-in-devdependencies` judges the whole manifest rather than the diff, so it fired on
every zack.land PR until the dependency move landed and is left out. Directional: two small
repositories, one author.

### 3. Mutation testing of the catalog's own tests (`mutation_score.py`)

Each mutant flips one operator or constant in a gate; a mutant the gate's tests still pass is a
survivor. Before this PR:

| Gate | Killed |
|---|---|
| `_acceptance.py` (verdict grammar) | 32 of 43 |
| `acceptance_verdict.py` | 29 of 38 |
| `qae_artifacts.py` | 53 of 60 |
| `new_source_has_test.py` | 20 of 23 |
| `branch_name_length.py` | 12 of 17 |
| `review_receipt.py` | 10 of 17 |

Most survivors are equivalent: a changed message, or a `required` flag whose absence ends in the
same exit 2. Four were real gaps on documented rules, and this PR adds a test for each:

- The artifact-escape test anchored to `../../etc/passwd:1`, which never parses as an anchor, so it
  passed without reaching the containment check. Turning that check's `and` into `or` let a path
  outside `--artifacts` resolve, and every test still passed.
- An anchor inside parentheses, the shape the QAE prompt asks the explorer to write, was untested.
- An empty screenshot and a response of exactly 400 were untested boundaries.

After the new tests: `_acceptance.py` 37 of 43, `acceptance_verdict.py` 30 of 38,
`qae_artifacts.py` 55 of 60. Remaining real gaps, not fixed here: the plain-list criteria format,
line counting for a file with no trailing newline, an anchor to line 1, and the push-event branch
name in `branch-name-length`.

### 4. Pattern eval: do agents copy the nearest example?

A small shop backend where handlers must read through a repository layer (it drops soft-deleted
rows) and require sign-in, next to legacy exports that do neither. The task, identical in every arm:
"add a CSV export of invoices, like the other exports". Four arms differed in one variable: nothing;
the rules in AGENTS.md; a structural test whose failure names the fix, with the legacy files on a
baseline list; or the legacy exports rewritten to the pattern. Two rounds (one legacy file, then a
cluster of three), three agents per arm, the parent model, scored by a checker the agents never saw.

- **All 24 agents followed the pattern** in every arm. On a codebase small enough to read whole, the
  mechanism made no difference, and several agents in the "nothing" arm flagged the legacy exports
  as bugs.
- **They copied what no rule covered.** With three clean, consistent exports nearby, 0 of 3 agents
  quoted CSV values and 0 of 3 wrote amounts with two decimals, matching the examples, latent bug
  included. In the structural-test arms 6 of 6 did both.

So the measured risk is not that a capable agent ignores a visible rule; it is that it faithfully
copies whatever the surrounding code does in every respect nobody checks. This setup cannot test
the large-repository drift OpenAI describes, where agents see only the files they open.

## Recommendations

Ranked by evidence times impact over cost.

1. **Measure rework before and after every new gate.** Run `pr_outcomes.py` monthly on each
   subscribed repository, and adopt a `Fixes: #N` line in fix PR bodies so a candidate link becomes a
   verified one. Lands in this directory and in the fleet's PR template; costs nothing in CI.
2. **Add a regression lane to the QAE harness.** Keep a feature map in the consumer (one file per
   user-facing feature: how to reach it, what end state proves it), have the explorer replay the
   features the diff touches on both the PR head and the base, and judge both with the existing
   artifact gates. This is the missing PASS_TO_PASS half. Lands in `harnesses/qae/` as a new declared
   input; needs a pilot consumer first.
3. **Propose a diff-scoped PR-size gate, in `--soak`.** It is the only signal in the backtest that
   tracked rework, and the literature agrees. Per the catalog rule it enters when three live
   repositories want it; until then it can run as a soak line in this repository and zack.land.
4. **Teach consumers to write structural tests with remediation messages and a shrinking baseline.**
   Boundary rules differ per codebase, so these live in each consumer; the catalog documents the
   pattern and, once three repositories carry a rules file, ships a generic runner as a ratchet.
   When adding one, rewrite the nearest examples too, because agents copy them.
5. **Score test quality where tests change.** A tree-only check for test cases with no value
   assertion fits the gate contract; prototype it against consumer history and hand-label its
   precision before it enters. Diff-scoped mutation testing, Google style (surviving mutants as
   findings, never a score threshold), needs to run the consumer's tests, so it belongs in a harness.
6. **Run a second, independent review only where it pays.** On PRs above a size threshold, add one
   reviewer from a different model family to the review harness. Expect roughly half of defects per
   reviewer and little gain beyond two or three.
7. **Measure before carrying a review receipt across a rebase by patch-id.** No published evidence
   either way; log how often a carried verdict is followed by a fix before relying on it.

## What not to do

- **Answer a repeated mistake with more AGENTS.md text.** It costs tokens and decays within a session.
- **Gate on a mutation-score threshold.** No industrial source does; Google surfaces individual
  survivors.
- **Read `new-source-has-test` as a test-quality signal.** A test file that asserts nothing satisfies it.
- **Count PRs as success.** The 1,300, 1,500, and 2,500 figures above are output. Rework and
  follow-up fixes are the outcome.
